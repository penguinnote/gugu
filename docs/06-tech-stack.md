## 3. 왜 Supabase인가

### 3.1 RLS가 일급 시민이다

이 프로젝트의 핵심 설계는 **목장 격리를 코드가 아니라 데이터 계층에서 강제하는 것**이다(스키마 §1). Supabase는 RLS를 전제로 만들어진 제품이라 이 설계가 곁가지가 아니라 정석 경로가 된다.

애플리케이션 계층에서 막는 방식은 엔드포인트가 늘어날수록 누락 위험이 선형으로 증가한다. 기도제목을 다루는 앱에서 감수할 위험이 아니다.

### 3.2 카카오 로그인이 기본 제공된다

Supabase Auth가 카카오를 공식 지원한다. 직접 구현하면 며칠이 걸리는 일이 설정으로 끝난다. 구글도 마찬가지다.

### 3.3 운영할 서버가 없다

1인이 학기 중에 계속 손봐야 하는 프로젝트에서 서버 관리는 그 자체로 이탈 요인이다. DB·인증·스토리지가 관리형으로 묶여 있는 편이 낫다.

### 3.4 비용

100명 이하 규모는 무료 티어 안에 들어간다. 교회 사이드 프로젝트에서 월 구독료가 생기면 지속성이 흔들린다.

## 4. 핵심 구현 지점

### 4.1 열람과 집계의 분리 ★

스키마 §4.4에서 정한 가장 중요한 구조다.

- **열람** — RLS 정책으로 제한한다. 리더는 자기 목장에서 작성된 주간기록만 읽는다
- **집계** — `SECURITY DEFINER` 속성의 DB 함수로 처리한다. 이 함수는 RLS를 우회해 양의 전체 기록을 읽지만, **판정 결과만 반환하고 원문은 반환하지 않는다**

리더는 "이 양은 접촉 공백 상태"라는 사실은 알 수 있고, 그 근거가 된 다른 목장의 기록은 볼 수 없다. 이 분리가 제대로 구현되지 않으면 지표가 틀리거나 정보가 샌다.

> 포트폴리오에서 설명할 가치가 가장 큰 부분이다.

### 4.2 웹 푸시는 직접 구현한다

Supabase는 푸시 발송 기능을 제공하지 않는다.

- 구독 정보(`User.푸시 구독 정보`)는 DB에 저장
- 발송은 Edge Function에서 VAPID 키로 직접
- 월요일 배치는 pg_cron 또는 Vercel Cron이 그 함수를 호출

iOS는 홈 화면에 추가해야만 구독이 생성된다(PRD §11). 구독이 없는 리더를 운영자 화면(A-1c)에서 식별할 수 있어야 한다.

> **구현 (2026-10-03, Step 7) — 위 계획에서 바꾼 것**
>
> - **발송은 Edge Function 이 아니라 Next(Vercel)의 서버 코드** — `web-push` + VAPID(`src/lib/push/send.ts`). 제출·스탬프 알림은 서버 액션의 `after()` 에서, 월요일 알림은 `/api/cron/reminder` 를 **Vercel Cron**(`vercel.json`, 월 11:00 UTC = 20:00 KST)이 부른다. 수요일 아침 목사님 주간 정리 알림은 `/api/cron/digest`(화 22:00 UTC = 수 07:00 KST, 2026-11-05 — 받는 사람 `push_digest_targets`). 배포 대상이 하나로 남고, 알림 문구·받는 사람 로직이 앱 코드와 같은 테스트(vitest·PGlite)를 탄다.
> - **Serwist 대신 손으로 쓴 `public/sw.js`** — 푸시와 알림 클릭, 그리고 앱 시작 페이지(2026-11-01)만 한다. 시작 페이지(`public/launch.html` · `launch-icon.svg`)만 기기에 담아 두었다가 바깥에서 들어온 `/` 열기에 곧바로 내준다 — 서버가 첫 화면을 만드는 동안의 흰 백지를 없애려고. 시작 페이지는 최소 1.4초 떠 있고(2026-11-04), 그동안 `/` 를 미리 받아 두었다가 내준다(2026-11-02). 서비스 워커는 이제 모든 기기에 건다(`components/sw-register`). 그 밖의 오프라인 캐시는 MVP 범위 밖(05 §1.2)이라 Serwist 가 해 줄 일이 없다.
> - **구독은 `users` 한 칸이 아니라 `push_subscriptions`(기기별)** — 폰·PC 둘 다 받을 수 있다. 쓰기는 함수로만, 읽기는 본인 것만. 발송은 서버 전용 키(`SUPABASE_SECRET_KEY`, `src/lib/supabase/admin.ts`)로.
> - **같은 알림은 한 번** — `push_log (dedupe_key, user_id)` 유일. 크론이 두 번 돌거나 다시 제출해도 한 번.
> - 키가 없으면 알림만 건너뛴다 — 제출·스탬프는 알림 때문에 실패하지 않는다.

### 4.3 신청·승인 가입

Supabase Auth는 기본적으로 자유가입을 허용한다. **막지 않는다.** 대신 가입한 계정이 승인 전에는 아무것도 못 보게 한다.

- 첫 로그인에 `ensure_user()` 가 `pending` 앱 계정을 만든다. 이름·제공자는 클라이언트가 아니라 `auth` 스키마에서 읽는다
- `pending` 은 청년부 프로필과 신청 화면만 본다 — RLS 의 "승인된 사용자" 판정(`is_app_user()`)이 걸러낸다
- 리더 명단에서 자기 이름을 고르면(`apply_for_person`) **운영자가** 승인한다(`approve_application`) — 결과는 곧바로 leader. 조건부 UPDATE 한 번으로 연결과 검증을 처리해 같은 사람에게 두 계정이 붙는 경쟁을 막는다. 청년은 신청 대상이 아니다(앱을 쓰지 않는다)
- 리더 권한은 승인으로만 생긴다. 내리는 건 `unlink_person_account`(운영자)
- 신원 컬럼(`role` · `provider` · `auth_user_id`)은 일반 UPDATE 권한에서 빼서 위 함수로만 바뀌게 한다

> 2026-09-27 이전에는 초대 토큰 방식이었다. 한때 청년도 앱을 쓰기로 해 운영자가 80명에게 링크를 보내는 구조가 병목이 되어 바꿨고, 같은 날 청년 사용을 접었지만 신청·승인은 유지했다 — 41명이어도 리더 본인이 고르는 편이 초대 토큰보다 싸다(04-schema §0).

> **2026-10-30 — 시작 화면에서 역할을 고른다.** 목사님 · 임원진 · 리더 중 하나를 고르고 운영자가 승인한다. 목사님은 이름 없이 신청하고 승인되면 `pastor`. 임원진은 리더를 겸하면 이름을 골라 `leader` + `is_officer`, 아니면 `officer`. `is_officer` 도 승인 함수로만 켜진다. 같은 원칙 — 신원은 함수로만 바뀐다 — 을 그대로 썼다.

### 4.4 Excel과 PDF

| 산출물 | 방식 | 이유 |
|---|---|---|
| Excel | SheetJS로 클라이언트에서 생성 | 서버 부담 없음. 100명 이하 규모에서 충분 |
| PDF | 인쇄용 CSS + 브라우저 인쇄 | 한글 폰트·레이아웃 처리 비용 회피 (IA §4) |

두 경우 모두 대외비 표기와 다운로드 로그 기록이 함께 가야 한다(PRD §10).

> **바뀜 — 둘 다 서버에서 만든다**
>
> - **Excel = `exceljs`, 라우트 핸들러에서** (`/export/xlsx`, `src/lib/export/xlsx.ts`). 시트 5장(요약 · 출석 · 개인별 · 기도제목 · 특이사항, 2026-10-29). 숫자 칸은 `COUNTIF` · `COUNTIFS` 함수이고 계산값도 함께 넣는다. 색 · 고정 · 필터 같은 서식이 필요해 SheetJS 무료판으로는 부족했다. 휴대폰에서는 받자마자 공유 시트가 뜬다.
> - **명단 엑셀 (2026-10-28)** — 교회가 쓰던 명단 엑셀(`명단_및_현황`)과 같은 모양을 같은 라이브러리로 만든다(`src/lib/export/roster-xlsx.ts`, `/export/roster`). 전체 명단은 목사님 · 운영자 · 임원진, 목장 명단은 그 목장 리더도.
> - **PDF = `@react-pdf/renderer` (2026-10-29)** — 인쇄용 화면을 걷고 서버에서 PDF 파일을 만든다(`src/lib/export/pdf.tsx`, `/export/pdf`). 휴대폰은 인쇄보다 파일 공유가 쉽다. 한글은 Pretendard(OFL)를 파일로 싣는다 — `next.config.ts` 의 `outputFileTracingIncludes` 가 그 경로 함수에 글꼴을 같이 담는다. 모든 페이지 아래 대외비 표기와 쪽 번호.
> - **로그가 먼저다** — `log_export()` · `log_roster_export()` 가 실패하면 내보내지 않는다. 원래 원칙 그대로다.

### 4.5 시간·로케일 값은 하이드레이션 위험이다 ★

같은 컴포넌트를 서버와 브라우저가 한 번씩 그리고, React 는 두 결과가 글자 하나까지 같아야 한다. **시간과 로케일에 기대는 값은 두 곳에서 다르게 나오기 쉽고, 다르면 하이드레이션이 깨진다** — 화면이 다시 그려지고 콘솔에 오류가 남는다. 2026-09-27 하루에 두 번 겪었다: 마감 카운트다운(`new Date()` 로 시작해 서버와 브라우저의 '지금' 이 달랐다), 제출 시각(`Intl.DateTimeFormat("ko-KR")` 이 Node ICU 에서는 `AM 5:00`, 브라우저에서는 `오전 5:00`).

화면에 시간·로케일 의존 값을 그릴 때 지킬 것:

1. **'지금' 은 서버가 정한다.** 클라이언트 컴포넌트는 `serverNow` 같은 prop 으로 서버 렌더 시각을 받아 첫 렌더에 그대로 쓰고, 클라이언트 시계로는 마운트 뒤(`useEffect` + `setTimeout(…, 0)`)에 바꾼다. `useState(() => new Date())` 는 금지.
2. **`Intl` · `toLocaleString` · `toLocaleDateString` 을 화면 문자열에 쓰지 않는다.** Node 와 브라우저의 ICU 데이터가 다르다. 한국어 날짜·시각은 `src/lib/week.ts` 의 KST 헬퍼처럼 **UTC+9 를 더해 숫자를 직접 조립**한다("오후 3:12", "9월 25일").
3. **시간대는 항상 KST 로 고정**한다. 기기 시간대를 읽지 않는다 — 서버(Vercel)는 UTC 다.
4. **`localStorage` · `window` · 기기 설정은 첫 렌더에서 읽지 않는다.** 서버에는 없다. 읽어야 하면 마운트 뒤에 읽고, 그때까지는 서버 값으로 그린다.
5. 시간 의존 화면을 만들면 **새로고침 뒤 콘솔에 "Hydration failed" 가 없는지** 확인 항목에 넣는다(09 §2.0).

### 4.6 브랜치 프리뷰로 실측한다 (2026-09-30)

화면 검증을 로컬 개발 서버 + 브라우저 창에서 하면 그때마다 사람이 로그인해 줘야 해서 매번 막힌다. 브랜치를 push 하면 Vercel 이 프리뷰를 만들고, 그 URL 에서 직접 클릭·스크린샷·콘솔을 본다. 남은 단계가 전부 화면 작업이라 계속 쓰인다.

```
브랜치에 push → 훅(verify) → Vercel 프리뷰 URL → 실측 → 통과하면 main 병합 → 프로덕션
```

- **main 에 직접 push 하지 않는다.** 단계마다 브랜치: `step-2-home`, `step-3-points` … pre-push 훅은 브랜치 push 에도 그대로 돈다.
- **★ 브랜치 별칭 URL 만 쓴다.** Vercel 은 커밋마다 고유 URL(`<프로젝트>-<해시>-<팀>.vercel.app`, 매번 바뀜)과 브랜치마다 고정 별칭(`<프로젝트>-git-<브랜치>-<팀>.vercel.app`)을 만든다. 커밋별 URL 은 origin 이 매번 바뀌어 쿠키가 날아가고 커밋할 때마다 다시 로그인해야 한다 — 그러면 이 흐름의 의미가 없다.
- **origin 규칙** (`src/lib/request-origin.ts`): `VERCEL_ENV=production` → `NEXT_PUBLIC_SITE_URL` 고정값(헤더를 조작해도 안 바뀐다 — 예전 localhost 사고의 재발 방지) · `VERCEL_ENV=preview` → `x-forwarded-host`/`x-forwarded-proto`(별칭 URL 이 곧 origin; 고정값을 쓰면 OAuth 콜백이 프로덕션으로 날아가 프리뷰에 영영 로그인할 수 없다) · 개발 → Host 헤더. 유닛 테스트 4건.
- **Supabase Redirect URL** 허용 목록에 `https://<프로젝트>-git-*-<팀>.vercel.app/**` 가 있어야 프리뷰 콜백이 거부되지 않는다. **Site URL 은 프로덕션 그대로 둔다.** 구글·카카오 쪽 리디렉션 URI 는 Supabase 의 `/auth/v1/callback` 을 가리키므로 손대지 않는다.
- Vercel 의 Preview 환경변수는 Production 과 같은 키가 전부 있어야 한다(`NEXT_PUBLIC_SUPABASE_URL` 등). `NEXT_PUBLIC_SITE_URL` 은 프리뷰가 쓰지 않지만 빌드가 읽으므로 프로덕션 값을 그대로 넣어 둔다.
- **프리뷰는 프로덕션 DB 를 본다 — 쓰기는 앱이 막는다 (2026-10-06, Step 9c).** 같은 Supabase 프로젝트라 프리뷰 실측 한 번이 리더의 실제 기록을 오염시킬 수 있다. Supabase 클라이언트 둘(`lib/supabase/server.ts`·`admin.ts`)의 fetch 를 `guardFetch`(`lib/preview-guard.ts`)로 감싸, `VERCEL_ENV=preview` 이고 `PREVIEW_WRITES` 가 `allow` 가 아니면 `/rest/v1` 쓰기·쓰기용 rpc·`/storage/v1` 쓰기를 원래 요청 없이 403(`PREVIEW_READONLY`)으로 돌려준다. 읽기와 로그인(`/auth/v1`, `ensure_user`)은 통과하고, 헤더에 '프리뷰 · 읽기 전용' 이 붙는다. rpc 는 `lib/rpc-classes.json` 의 분류(읽기용·로그인용·쓰기용)를 따르고, 분류에 없으면 쓰기로 본다. 앱이 부르는 rpc 가 모두 분류됐는지, 읽기용이 DB 에서 stable/immutable 인지 테스트가 본다.
  - **출시 전**: Vercel Preview 에 `PREVIEW_WRITES=allow` — 실측에 쓰기가 필요하다. **출시 때 이 변수를 지운다**(09 §2.12). 브랜치 하나만 막아 보려면 그 브랜치를 push 한 뒤 `vercel env add PREVIEW_WRITES preview --git-branch <브랜치>` 에 `block`, 끝나면 `vercel env rm PREVIEW_WRITES preview <브랜치> --yes`.
  - 남는 구멍: 프리뷰 브라우저에서 세션 토큰으로 PostgREST 를 직접 치는 경우. 앱 코드는 그러지 않는다. **로컬 개발(`npm run dev`)도 프로덕션 DB 를 본다** — `VERCEL_ENV` 가 없어 막히지 않는다. 출시 뒤 로컬에서 쓰기를 시험하려면 따로 결정한다.
- 실측을 넘길 때의 보고 형식은 09 §2.0a.

### 4.7 로뎀 월드 — Three.js 한 파일 + 같은 출처 iframe (2026-10-08~)

- **`public/rodem-world/index.html` 한 파일**에 Three.js 0.158(jsDelivr 스크립트)로 그린다. 시안으로 시작해 그대로 자랐다. 번들러를 타지 않아 앱 빌드와 따로 고친다.
- **`/world` 가 같은 출처 iframe 으로 띄운다** (`src/app/world/`). 월드의 전역·스타일이 앱과 섞이지 않는다. 앱 껍데기는 불러오기 화면 · 나가기 · 보고서 연결 · 서버 액션만 맡는다. 월드가 부탁하면 껍데기가 서버 액션 → DB 함수를 부르고 새 상태를 돌려준다. 월드는 DB 를 직접 만지지 않는다.
- **휴대폰 무게 예산** — `?stats` 로 초당 장 수 · 그리기 횟수 · 세모 수를 잰다. 시작 화면 세모 78만 → 25만(2026-10-08). 멀리 있는 마을은 단순한 모양(LOD, 마을당 1.2만~1.7만 → 약 1천, 2026-10-10). 아바타 조각 굽기 · 길 한 덩어리로 그리기 25~30% 덜기(2026-10-15).
- **해상도 자동** — 화질 '자동' 은 기기 해상도(최대 2배)로 시작한다. 초당 50장 아래면 해상도를 0.25씩 1까지 내리고, 그래도 45장 아래면 들꽃 같은 장식을 숨긴다. '가볍게' · '선명하게' 는 사용자가 고른다.
- **외부 그림·소리는 CC0 만** — 가구는 KayKit · Tiny Treats(CC0), 동물 소리는 Freesound CC0 녹음. 출처는 각 폴더의 `CREDITS.txt`.
- **열매 경제는 DB 에 있다** — 원장 · 상점 물건 · 가진 물건 · 마을 꾸밈 · 옷장 · 집 안 가구가 모두 마이그레이션과 RLS 테스트를 탄다(04). 규칙 값은 `world_rules` 표.
- **월드가 찍은 사진을 앱이 쓴다 (2026-10-24~25)** — 목장 탭 머리 = 우리 집 안 사진(`world_room_shots`), 정보 탭 = 내 아바타 사진(`world_avatar_shots`). WebP 를 DB `bytea` 로 둔다(목장·사람마다 한 장, 600KB 이하). Storage 를 따로 쓰지 않는다.
- 되돌림 지점: 태그 `pre-world-2026-10-08`.

### 4.12 AI 주간 정리 — Claude API (2026-11-07)

목사님 주간 정리 v2(01 §9). 저장 · 권한은 04 §3.12.

**왜 Claude API 인가**

- **응답을 JSON 스키마로 받는다**(structured outputs — `output_config.format`). 네 칸 · 근거 기호가 정해진 모양으로 와서, 코드가 항목마다 검사하고 틀린 것만 버릴 수 있다. 정리 한 번이 요청 한 번이라 에이전트 · 도구 호출이 필요 없다.
- **API 로 보낸 자료를 학습에 쓰지 않는다**(아래 보관 조건). 기도제목을 보내는 이상 이것이 먼저다.
- **지시를 지키는지 재 볼 수 있다** — 한국어 요약, 판정하지 않기, 모든 항목에 근거 달기를 가짜 자료 평가(`npm run eval:digest`)로 확인했다.
- **따로 띄울 것이 없다** — 공식 SDK(`@anthropic-ai/sdk`)를 Next 서버 코드에서 한 번 부른다. Vercel 함수 그대로, 서버 · 큐를 더하지 않는다.

**모델** — 기본 **`claude-sonnet-5-5`, effort `medium`**(`src/lib/ai/digest-call.ts`).

- 환경변수 `DIGEST_MODEL`(`claude-sonnet-5-5` · `claude-haiku-5-5` 만) · `DIGEST_EFFORT`(`low` ~ `max`)로 바꿀 수 있고, 없거나 모르는 값이면 기본으로 돌아간다(`.env.example`). 소넷 5.5 의 기본 effort 는 high 지만 정리에는 medium 으로 충분했다.
- temperature 는 보내지 않는다. 거절(`stop_reason: refusal`) · 길이 초과를 내용보다 먼저 본다. 소넷만 서버 쪽 대체 모델(`fallbacks`)을 켠다.
- 비용 — 큰 가짜 자료(12목장 · 85명) 평가에서 소넷은 주당 약 $0.03, 한 해 약 $1.5.

**하이쿠(`claude-haiku-5-5`)를 쓰지 않은 이유** — 같은 큰 가짜 자료로 소넷과 나란히 평가했다(`EVAL_MODELS`, 2026-11-07, 결과는 `eval/digest/out/`).

- **다른 사람의 일로 적은 항목이 나왔다** — 한 사람의 메모 내용을 같은 목장의 다른 사람 일로 적었다(2차 평가 09-27 주).
- **이름 없는 항목이 나왔다** — 마지막 평가에서 하이쿠는 6개가 '근거와 사람 불일치'로 버려졌고 그중 5개가 사람 없이 쓴 항목이었다. 소넷은 0개.
- 그 밖에 입력에 없는 '자매' 호칭을 붙였고(성별을 모른다), 처음에는 함께 기도할 제목을 거의 모두 옮겨 상한까지 채웠다.
- 값은 소넷의 약 1/9(마지막 평가 6주 $0.019 대 $0.168)이지만, 소넷도 한 해 몇 달러라 아낄 이유가 작다.

## 5. 위험과 대응

### 5.1 무료 티어 프로젝트 일시 정지 ★

Supabase 무료 플랜은 일정 기간 활동이 없으면 프로젝트를 일시 정지한다. **주 1회 사용 패턴에서는 대체로 괜찮지만, 방학이나 휴주가 길어지면 위험하다.** 정지된 상태에서 리더가 접속하면 앱이 죽어 있다.

| 대응 | 내용 |
|---|---|
| 정기 핑 | 짧은 주기로 DB를 건드리는 스케줄을 둔다 |
| 사전 확인 | 방학 직전에 정지 정책을 확인하고 대비 |
| 최후 수단 | 유료 전환. 비용이 생기므로 마지막 선택지 |

> 요금제와 정지 정책은 자주 바뀐다. 개발 착수 시점에 반드시 재확인할 것.

> **2026-10-31 상태** — 별도 핑은 두지 않았다. 월요일 알림 크론이 매주 DB 를 읽는다. 방학 · 긴 휴주 전 확인은 여전히 남는다(§8).

> **2026-11-13** — 매일 밤 백업(§5.5)이 날마다 DB 에 접속해 덤프한다. 공식 문서 기준 "한 주 동안 DB 활동이 충분하지 않으면" 정지되므로, 이것이 사실상 매일 핑이다. 정지돼도 1년 안에는 되살릴 수 있다(문서 기준 — 2024 변경 기록은 90일이라 적었다).

### 5.2 RLS 설계 난이도

초기 학습 곡선이 있다. 정책을 잘못 쓰면 데이터가 안 보이거나(개발 지연) 다 보인다(사고). **권한 테스트를 개발 초기에 만들어두는 것이 필수다** — 리더 A가 리더 B의 목장 데이터를 읽으려 할 때 반드시 실패하는지.

### 5.3 벤더 종속

DB는 Postgres라 이전 가능성이 열려 있으나 **인증은 Supabase에 종속적**이다. 다른 곳으로 옮기면 계정을 다시 만들어야 한다. 100명 이하 규모에서 감수할 만한 수준이다.

### 5.4 한글 검색

전체 양 목록 검색(P-4)에서 한글 부분 일치가 필요하다. Postgres 기본 전문 검색은 한글에 약하므로, 80명 규모에서는 단순 `ILIKE` 패턴 매칭으로 충분하다. 과설계하지 않는다.

### 5.5 백업 (2026-10-31 추가)

Supabase 무료 요금제에는 자동 백업이 없어 직접 백업한다. 매일 데이터베이스를 내려받아 공개키로 암호화한 뒤 비공개 저장소에만 둔다. 비밀키는 저장소 밖에 있다. 백업도 기도제목을 담으므로 보관 기간은 기록 보관 약속(2년)보다 짧게 최대 1년으로 두고, 이 사실을 처리방침에 적었다. 정기적으로 임시 로컬 Supabase 에 되살려 행 수를 견준다.

## 6. 검토했으나 택하지 않은 것

### Django + React

Django admin이 관리 화면(A-1, A-1b)을 거의 공짜로 만들어준다는 점은 실제로 매력적이었다. 그러나

- **RLS와 궁합이 나쁘다.** ORM 위에서 행 수준 정책을 쓰려면 커넥션마다 세션 변수를 설정해야 하고, 커넥션 풀링과 충돌한다
- 배포처가 둘로 늘어난다 (프론트 + 백엔드)
- 신청·승인, 명단 관리 같은 화면은 어차피 커스텀이라 admin의 이점이 반감된다

격리가 이 제품의 정체성인 이상, admin 편의보다 RLS 적합성이 우선이다.

### Firebase

인증과 푸시가 잘 갖춰져 있으나 **RLS 같은 관계형 행 수준 정책이 없다.** 보안 규칙으로 흉내 낼 수는 있지만, 이 스펙의 집계·이력 요구를 문서형 DB로 다루면 복잡도가 급증한다.

### 애플리케이션 계층 권한 제어

가장 자유롭지만 가장 위험하다. 기도제목을 다루는 앱에서 "쿼리를 잘 짜면 된다"는 전제는 성립하지 않는다.
