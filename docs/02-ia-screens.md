> v0.88 — **집 꾸미기 다시** (2026-11-10, 사용자 요청). 집 안은 비어 있는 것이 기본 — 예전 기본 가구(침대 · 소파 · 책장 …)는 없고, 하나를 놓으면 기본 가구가 다 사라지던 혼란도 없어졌다. 내 집 안에선 빈 자리마다 반투명 + 와 아래 가운데 '집 꾸미기' 알약. 누르면 꾸미기 — 방을 위에서 내려다보고(메뉴 레일은 펼치지 않는다), 옆 창에 고른 자리('뒷벽 왼쪽' 등, ‹ › 로 넘김)에 맞는 가구 칸. 가구를 누르면 그 자리에 미리 놓여 보이고 아래 줄이 '되돌리기 · 놓기'(가진 것) / '열매 n 사서 놓기'(없는 것) / '열매 n개 모자라요'. 놓인 자리는 연필, 고른 자리는 라임 테, 놓인 것은 '치우기'로 가진 것에 돌려놓는다. 머리에 '다 꾸몄어요'. 월드 안에서 사는 곳(상점 · 꾸미기 입어 보기 · 집 꾸미기)은 모두 '열매 n개로 살까요?' 확인 창을 거친다(앱 상점은 전부터 물었다). 목장 탭 기본 그림(hd-room-blank)도 빈 방으로 다시 찍었다. 참고 — 동물의 숲(집 안 꾸미기 모드 · 보관함 · 바로 치우기), 심즈 모바일(놓을 자리 미리보기 · 사기 전 값), 모바일 집 꾸미기 게임들의 '고르고 → 미리 보고 → 확인' 흐름.

## 0. 설계 전제

- **목장은 이름으로 부른다.** DB 에는 "새싹" 만 저장하고 화면에서는 "새싹 목장" 으로 붙인다(`groupLabel()` 한 곳). "새싹 목장 보고서" 같은 조합이 자연스럽다. 번호(`groups.number`)는 정렬 전용 — 명단 등장 순서, 목사님이 매주 훑는 순서 (2026-09-28).

- 사용자는 **리더 40명대 · 목사님 · 운영자 · 임원진**이다. 청년(약 40명)은 앱을 쓰지 않는다 — 명단에 기록 대상으로만 있다(v0.5). 임원진(2026-10-30)은 목장 리더도 맡았으면 역할은 리더 그대로에 임원진 표시(`users.is_officer`)만 켜지고, 리더가 아니면 역할 자체가 임원진(`officer`)이다.
- 리더는 소속 목장 데이터만, 목사님은 전체를 본다. 임원진은 **전체 명단만** 본다(보고서 · 기도제목은 못 본다). 운영자는 관리 화면만 — 보고서 본문은 못 본다. 미승인 계정에게는 출석·보고서의 존재를 드러내지 않는다.
- 주 1회 사용이 기본 리듬. **홈 화면은 "이번 주에 할 일"을 보여주는 것이 전부**여야 한다.
- 모바일 우선(PWA). 모든 화면은 한 손 조작 기준.

### 하단 탭 4개 — 홈 / 목장 / 상점 / 정보 (확정 2026-09-27)

```
[ 홈 ]   [ 목장 ]   [ 상점 ]   [ 정보 ]
```

탭은 **리더 기준 하나**다. 목사님·운영자·임원진은 같은 네 갈래에서 내용이 다를 뿐이다. (v0.4 의 "탭은 역할 무관" 원칙은 청년에게 보고서의 존재를 숨기기 위한 것이었고, 청년이 앱을 쓰지 않게 되면서 근거가 사라져 뺐다 — v0.5.)

- **홈** — 앱을 여는 순간 **자기 연속 기록(streak)이 보여야** 지속성 장치가 작동한다. 그래서 랭킹은 별도 탭이 아니라 홈 안이다.
- **목장** — 우리 목장과 전체 목장 프로필. 격리 원칙의 예외 구역(§4)이 이 탭에 모인다.
- **상점** — 포인트 아이템, streak freeze 쿠폰.
- **정보** — 내 프로필, 승인 관리(권한 있으면), 설정, 로그아웃. 관리·내보내기처럼 "가끔 하는 일" 도 여기다.

> **1단계 골격 구현 (2026-09-29)** — `components/tab-bar.tsx`, 하단 고정, safe-area 반영, 텍스트만(아이콘·색은 7단계 디자인 패스). **4탭 고정** — 앞선 "내용이 있는 탭만" 결정을 뒤집었다: 앞으로 홈·목장·상점·정보가 다 들어오므로 틀을 먼저 세우고, 상점은 자리표시("준비 중")로 둔다. 탭바가 보이는 화면은 `app/(tabs)` 라우트 그룹 안, 로그인·신청(`/login`, `/apply`)은 밖. 상단 헤더(앱 이름 · 내 정보)는 그대로.
>
> **홈과 지난 기록의 분리 (2단계, 2026-09-30)** — 홈은 새 화면이 아니라 두 화면의 요약부를 역할별로 재배치한 것이다.
>
> | 경로 | 답하는 질문 | 내용 |
> |---|---|---|
> | `/` | **지금 뭘 해야 하나** — 이번 주 한 건 | 리더: 마감 카운트다운("제출까지 2일 3시간" / "이번 주 마감됨") → 이번 주 상태(미제출: "아직 안 쓰셨어요" + **작성하기** 큰 버튼 / 제출: "제출 완료" + 제출 시각 + 목사님 확인·스탬프, 아직이면 표시 없음) → streak 줄(제출 직후 돌아오면 한 번 강조) → 지난 보고서 3건 + 전체 보기. 목사님: "12목장 중 8곳 제출 · 4곳 미제출" 한 줄 + 12목장 카드(N주 연속 · 읽음 여부). 운영자 겸임(admin + 명단 리더)은 리더 홈 — 운영 메뉴는 정보 탭 |

## 3. 핵심 플로우

### 3.1 주간 제출 — 가장 중요한 경로

```
알림(월요일 — 화요일 마감 전날)
  → L-1 홈 "이번 주 보고서 작성" 버튼
    → L-2 한 화면: 사람마다 출석 3단 · 기도제목(지난 기도제목이 흐리게) · 1대1
    → 제출
  → 목장 리더 전원에게 "OO가 제출했습니다" 알림
```

**목표: 3분 이내.** 이 경로의 탭 수와 스크롤 양이 제품의 성패를 좌우한다.

설계 원칙 두 가지:
- **출석 체크와 기도제목 입력을 분리하지 않는다.** 한 화면에서 양 이름 옆 토글을 누르고, 필요한 사람만 펼쳐서 기록한다. 화면을 나누면 왕복이 늘어난다.
- **출석은 칩 넷이다(v0.82, 2026-10-30)** — `현장 예배 · 온라인 예배 · 목장 모임 불참 · 결석`. 예배는 현장 · 온라인 · 결석 중 하나, 불참은 현장 예배에 덧붙는 표시(온라인은 불참을 자동으로 켜고 잠근다), 결석은 혼자. 온라인 · 불참 · 결석에는 사유 칸이 하나씩(`lib/attendance.ts`). 기본값이 없는 것은 그대로다. 아래는 그 전 3단 시절의 결정이다. **출석은 3단 세그먼트.** `출석 / 예배만 / 결석`. 한 번 탭에 확정하고 순환하지 않는다. **기본값은 없다** — 사람마다 한 번 탭해야 제출할 수 있다(Step 4 확정 ①, PRD §6.7 의 기본값 '예배+목장'을 뒤집었다). 기본값이 있으면 손대지 않은 사람이 출석으로 굳는다.
- **빈 기도제목을 강조하지 않는다.** 붉은 테두리·경고 아이콘·'미작성 N명' 없음. 빈칸이 눈에 띄면 "말 못 할 사정이 있다" 는 추론 경로가 생긴다. 필수 항목이 비었을 때만 제출 시점에 한 줄로 안내한다.
- **지난 기도제목은 가장 최근에 기록이 있는 주차**를 흐리게 보여준다. 2주 이상 건너뛰었으면 'N주 전'. 기록이 없으면 그 자리가 비어 있다 — '기록 없음' 같은 문구 없음. '이어서 쓰기' 로 복사할 수는 있지만 기본값으로 채우지 않는다.
- **1대1 접촉은 별도 체크.** 목장모임 참석 여부와 무관하며, 결석한 양도 체크 대상이다. 1대1이면 카톡 한 줄도 접촉이고, 단톡방 공지는 아니다. 챙김이 필요한 양 지표의 핵심 입력값(지표 정의서 §3.1.1).
- **기도제목은 목장모임 참석자만 필수.** 예배만 드리고 간 양이나 결석자에게 기도제목을 강요하면 리더가 지어낸다. 특이사항은 언제나 선택.

### 3.2 목사님 반응 루프

```
P-1 제출 현황 (제출 11/12 · 미제출 1)
  → 카드 탭 → P-3 보고서 상세  ← 이 서버 렌더가 곧 '읽음' (first_read_at 고정)
    → 스탬프 한 탭 = 찍고 다음 목장으로 (제출된 목장만 순회, 마지막이면 현황)
    → 연타 감지: 목장당 열람 시간 중앙값 (03 §2.2c)
  → L-2 리더 화면 맨 위: "✓ 지난주 보고서를 목사님이 확인하셨습니다 · 화요일 · "기도하겠습니다""
  → (Step 7) 해당 목장 리더 전원에게 알림
```

이 루프가 끊기면 리텐션 장치가 사라진다(PRD §6.3). 성공 기준은 "잘 보이는가" 가 아니라 **"본 흔적이 리더에게 닿는가"** 다. 목사님이 매주 12개에 글을 쓰는 설계는 반드시 다시 0 이 되므로 반응은 한 탭이고, 읽음은 자동이다. 12개를 훑는 비용: 제출된 목장 N 개에 **첫 카드 1탭 + 스탬프 N탭 = N+1** (10개 제출이면 11탭). 스탬프가 '다음' 을 겸하므로 연타 위험이 있다 — 막지 않고 03 §2.2c 로 관찰한다.


보고서 내려받기는 목사님(고른 목장)과 리더(자기 목장 하나 — 목장 칸 대신 '○○ 목장' 한 줄, 2026-10-14)가 쓴다. 운영자 · 임원진은 404. 명단 엑셀은 보고서 본문(출석 · 기도제목)이 없는 교회 명단 꼴이다.

**이 화면이 제품의 가장 큰 데이터 유출 지점이다.** 앱 내부의 격리 설계가 아무리 촘촘해도 파일 한 번 내려받으면 통제 밖으로 나간다. 그래서 편의보다 마찰을 우선한다.

| 통제 | 내용 |
|---|---|
| 범위 선택 강제 | 전체 일괄 버튼 없음. 기간·목장을 매번 고른다 |
| 대외비 표기 | PDF는 모든 페이지 하단 워터마크, Excel은 시트 첫 행 고정 — `대외비 · YYYY-MM-DD 다운로드 · <이름>` |
| 다운로드 로그 | 누가·언제·어느 범위를 받았는지 기록 |

목사님은 앱 내에서 전체를 열람하므로, 내보내기에서도 **두 형식 모두 내용을 제한하지 않는다.** 다만 Excel은 정렬·필터·복사가 쉬워 유출 시 피해 규모가 크고 워터마크를 페이지에 새길 수 없다. 따라서 Excel 쪽은 **다운로드 로그와 시트 상단 대외비 표기**가 통제의 중심이 된다.

## 4. 화면별 유의사항

**L-5 / L-5a 목장 프로필** — 목장 간 격리 원칙(PRD §7)의 **예외 구역**이다. 승인된 전원(리더 41명·목사님·운영자, 2026-10-30 부터 임원진도)이 12개 목장 프로필을 열람하며, 이것이 Phase 3 꾸미기 보상이 작동하기 위한 전제다(꾸민 것을 남이 봐야 보상이 된다). **v0.5 에서 관객이 청년 80명에서 리더 41명으로 줄었다** — 꾸미기·리더보드의 보상 설계는 Phase 3 에서 이 전제로 다시 본다.

노출 범위는 **멤버 이름·성별·소속·목장 내 역할까지**로 제한한다. 출석 이력, 기도제목, 특이사항은 절대 이 화면에 오르지 않는다.

**자유 글은 목장 소개 용도다.** 기도제목이나 개인 사정은 여기 쓰지 않는다 — 그것은 주간 보고서의 자리다. 용도가 그렇게 정해져 있으므로 화면에 열람 범위 경고나 주의 문구를 넣지 않는다(2026-09-27). 리더 전체·목사님이 읽는 공개 영역이다. 용도가 정해진 블록 구조는 유지한다 — 자유 캔버스 하나보다 쓰기 쉽고 읽기 쉽다.

| 방어 | 내용 |
|---|---|
| **블록 구조** | 자유 캔버스 하나가 아니라 용도가 정해진 블록 조합으로 구성한다 |
| 내리기 권한 | 목사님·운영자가 부적절한 내용을 삭제할 수 있다 |

블록 구성:

| 블록 | 내용 | 단계 |
|---|---|---|
| 목장 소개 | 짧은 한두 줄 | MVP |
| 멤버 목록 | 이름만 자동 표시 | MVP |
| 디데이 | 제목 + 날짜, 복수 등록 | MVP |
| 테마 찬양 | 제목 + 링크 | MVP |
| 자유 글 | 텍스트. 리더 전체·목사님이 읽는 공개 영역 | MVP |
| 배경·글씨체·스티커 | 상점에서 획득 | Phase 3 |

**이미지 업로드**는 교회의 기존 사진 관련 관행을 따른다. 별도 동의 절차는 두지 않는다.

> **구현 (2026-10-05, Step 8)** — `/groups` 아래 **전체 목장** 12카드(명단 순서, 우리 목장 표시, 리더 n · 청년 m · 소개 한 줄 · 가장 가까운 디데이). 식별자는 이름 — `/groups/새싹`, 편집은 `/groups/새싹/edit`. 홈 → 목장 탭 → 카드 → 프로필 2탭, 편집 → 저장 +2탭. 블록 다섯이 한 화면에 있고 **빈 블록은 통째로 숨긴다** — 다 비면 "아직 소개가 없습니다" 와 (고칠 수 있으면) '채우기'. 멤버 목록은 `persons_public` 에서 이름만 — 목장장 → 리더 → 청년, 이름순. 휴면·기록 제외는 어떤 식으로도 드러내지 않는다. 디데이는 오늘 이후만 보이고(D-DAY · D-n), 지난 것은 편집 화면에만 '지남' 으로 남아 지울 수 있다. 편집은 자기 목장 리더 + **'내리기' 권한의 목사님·운영자**(별도 버튼 없이 같은 편집 화면에서 지운다), 그 외 404. 저장은 하단 고정 버튼 하나, `updated_at` 낙관적 잠금 — 두 리더가 동시에 고치면 나중 사람이 "다시 열어 주세요" 를 본다. 한도(소개 100자 · 자유 글 1000자 · 디데이 10 · 찬양 5, http(s) 링크만)는 DB 제약과 같은 숫자다(04 v0.17). 프로덕션의 프로필 행은 0개에서 시작한다 — 첫 편집이 insert 다. 청년부 프로필(L-5c)은 Step 9 에서 운영자 편집 화면과 같이 들어온다.

> **삭제 (2026-11-26, 사용자 결정)** — `/admin/org-profile` · 전체 메뉴 줄 · 전체 목장 맨 위 블록을 지우고 `org_profile` 표도 마이그레이션으로 지웠다. 아래 구현 기록은 옛 내용이다.

> **구현 (2026-10-06, Step 9a)** — 목장 탭 맨 위 블록 하나: 소개 · 다가오는 디데이 · 공지(자유 글). 찬양은 블록에 넣지 않는다(훑는 화면이라 짧아야 한다). 비어 있으면 운영자에게만 '채우기', 다른 사람에겐 블록 자체가 없다. 편집은 `/admin/org-profile` — 목장 프로필과 같은 폼(`ProfileForm`), 저장 액션만 다르다. 미승인(pending)은 `/apply` 만 보므로 아직 청년부 프로필을 보지 못한다 — 04 §3.5 의 "미승인자에게 보이는 유일한 것" 은 신청 화면에 블록을 얹을 때 성립한다(미정).

**A-1 명단 관리** — `/admin/people`: 목장별 전원, 한 줄에 이름·역할과 **기본값이 아닌 표시만**(목장장 · 활동 외 상태 · 판정 태그 · 확인 필요 · 계정). 필터 다섯(전체 · 확인 필요 · 리더 · 계정 연결 · 활동 외·태그). `/admin/people/[id]`: 소속 이동 · 리더↔청년 · 목장장(목장당 한 명 — 지정하면 기존 목장장이 내려간다) · 상태(활동/휴면/**기록 제외**/이탈 — 기록 제외는 `set_person_recording` 로만, 과거 기록은 그대로) · 판정 태그(운영자만) · '확인 필요' 내리기 · 앱 계정(이름·제공자·권한, **연결 해제는 두 번 누른다**, 남의 계정이면 잠금). 저장 버튼 하나, 바뀐 게 없으면 나가지 않고, `updated_at` 낙관적 잠금. **(Step 11)** 목장을 옮기면 목장장은 해제되고, 상태 아래에 졸업·이사 = 이탈 · 입대 = 활동 + '군 복무' · 전역 = '재적' 안내, 계정 있는 사람을 이탈로 바꾸면 연결 해제 안내. 명단 위 '새 사람 등록' → `/admin/people/new`: 목장·이름·역할·성별 필수, 출생년도 선택, 미리 고른 값 없음, 같은 목장 동명이인은 거부(구분 표시를 붙여 등록), 저장하면 그 사람 상세로. DB 가 거부할 조합(계정 있는 리더 → 청년, 청년 목장장, 기록 제외의 들고남)은 저장 전에 말로 막는다. 출석·기도제목은 이 화면에 없다 — 운영자는 본문을 못 본다. **등록(새 사람)은 Step 11.** 09 §1.5·§1.5a 의 SQL 절차가 이 화면이 됐다 — 명단의 진실은 앱이다(08 Step 9 결정 ②).

**A-1b 휴주** — `/admin/weeks`. 이번 주부터 앞으로 12주, 한 줄에 주차·사유·켜기/끄기. 버튼이 곧 저장이다. **지난 주는 보여주지도, 바꾸지도 못한다**(2026-10-06 결정, DB 트리거) — 소급하면 streak 과 제출률이 바뀐다.

**A-1c 푸시 현황** — `/admin/push`. 계정 있는 리더·목사님을 미등록 먼저, 등록됨 다음으로. 기기 수와 마지막 성공 시각까지만 — endpoint·키는 운영자도 보지 않는다(`push_registration_status()`).

**L-2 보고서 작성** — 상단 "마감까지 …" 줄에 **연속 제출**이 붙는다: "마감까지 2일 · 3주 연속 제출 중". 제출하는 순간 액션이 새 값을 돌려줘 그 자리에서 "4주 연속 제출 중" 으로 바뀌고 짧게 강조된다 — 이 전환이 streak 의 유일한 보상이다(Step 6). 끊긴 뒤에는 "이번 주부터 다시", 첫 주(정시 제출 없음)에는 아무것도 없다 — 0 을 띄우지 않는다. 그 아래에 목사님 확인 줄(있을 때만). 순위는 없다 — 각 목장이 자기 기록만 본다. 홈 화면은 따로 없다 — 리더가 앱을 여는 이유는 보고서이고, 홈을 거치면 탭이 하나 는다. 지금 같이 열어둔 리더가 있으면 상단에 이름을 표시한다(60초 하트비트, `report_presence`). 초안과 제출을 구분하지 않고 버튼은 '제출' 하나다. 제출 후에도 같은 화면에서 고친다. **제출 버튼은 화면 하단에 고정**이고(12명 목장도 스크롤 없이 누른다), 미완성이어도 비활성으로 막지 않는다 — 버튼 위 한 줄에 "출석 미입력 2명" 처럼 **이름 없이 숫자만** 보이고, 누르면 첫 빈 곳으로 스크롤한다. 완료 메시지는 없다. **버튼 글자가 상태다** — `제출` → `제출됨`(흐림, 위 줄에 "오후 3:12 제출됨") → 고치면 `다시 제출`. 확인의 증거는 체크표시가 아니라 시각이다. 주차 이동(← 지난주 · 다음주 →)은 고정하지 않고 맨 위에 스크롤되게 둔다 — 드문 조작이다. 마감(화요일 23:59)이 지나도 저장은 되며 `is_late` 로 남고 "연속 기록에는 반영되지 않습니다" 한 줄이 뜬다. 두 리더가 같은 사람을 고치면 나중에 제출하는 쪽이 그 사람만 다시 확인한다 — 행 단위 `updated_at` 낙관적 잠금(04-schema §3.7). 입력 유실 방지로 브라우저 로컬에 임시 보관하되 서버 초안이 아니며 제출 시 지운다. **화면을 열면 항상 서버 값을 그린다** — 로컬 사본이 있으면 배너로 알리기만 하고 '복원' 을 눌러야 폼에 들어간다(먼저 덮어 그리면 배너를 못 본 사람이 남의 기도제목을 제출한다 — 2026-09-27 사고). 7일 지난 사본은 어느 보고서 화면을 열든 함께 지운다. 리더 본인 행의 1대1 체크는 비활성이다.

**L-4a / P-4a 양 상세** — 같은 화면이지만 보이는 범위가 다르다. 리더는 자기 목장 소속인 기간의 기록만, 목사님은 전체. 목장을 옮긴 양의 과거 기록 노출 규칙은 지표 정의서에서 확정한다.

**C-1 로그인 · C-4 신청 · L-9 승인** — **지금 (2026-10-30~)**: 처음 로그인한 미승인 계정은 `/apply` 에서 먼저 **목사님 · 임원진 · 리더** 중 하나를 고른다. 리더는 아래 그대로(목장 → 내 이름, `apply_for_person`). 목사님은 이름 없이 단추 하나(`request_role('pastor')`). 임원진은 목장 리더만 된다 — 리더처럼 이름을 고른다(`request_role('officer', 이름)`, 2026-11-01 부터 이름 없는 임원진 신청은 화면에서 막는다). 대기 화면은 신청한 역할(과 이름)을 보인다. 신청은 모두 `applications` 한 표에 `requested_role` 과 함께 쌓이고, 운영자가 `/approvals` 에서 역할 알약 · 로그인 방법을 보고 승인한다. 승인 결과 — 목사님 → `pastor`, 이름 없는 임원진 → `officer`, 이름 건 임원진 → 이름이 이어지고 `leader` + `is_officer`, 리더 → `leader`. `is_officer` 는 본인이 켤 수 없다(승인 함수만). 마이그레이션 `20261030030000_role_requests`, 테스트 `tests/rls/role-requests.test.mjs`. 아래 문단은 리더 신청의 원칙으로 그대로 맞다. 그 안의 "목사님은 승인하지 않는다" 는 목사님이 승인하는 사람이 아니라는 뜻이고, 목사님 계정 자체는 이제 신청 → 운영자 승인으로 들어온다(그 전에는 운영자가 SQL 로 역할을 줬다 — 09 §1.4).

가입은 막지 않는다. 처음 로그인하면 미승인(pending)이고 신청 화면밖에 못 본다(청년부 프로필은 2026-11-26 삭제). C-4 에서 소속 목장을 고르고 **그 목장의 리더 명단에서 자기 이름을 고른다** — 자유 입력이 아니라 목록 선택이라 오타·동명이인이 없다. 청년 이름은 목록에 없다(청년은 앱을 쓰지 않는다 — v0.5). 목록에는 이름과 생년월일을 보여 동명이인을 구분한다. L-9 의 승인은 **임명이 아니라 신원 확인**이다 — 명단의 그 리더와 로그인한 계정이 같은 사람인지. **운영자만** 확인하고 결과는 곧바로 leader 다. 목사님은 승인하지 않는다 — 보고서를 보러 들어오시지 계정을 승인하러 들어오시지 않으므로, 쓰지 않을 권한을 주면 실수 경로만 는다. 임명은 명단(A-1)이 한다 — 명단에서 리더를 올리거나 내리면 앱 권한이 따라간다(계정이 붙은 리더를 내리려면 먼저 연결을 뗀다).

같은 사람이 구글과 카카오로 각각 들어오면(이메일이 다르면) 별개 계정이 된다. **한 사람에 계정 둘은 DB 가 막는다**(04 §3.3) — 리더 41명 중 다수가 이 경우일 것이라 흔한 일이다. 두 번째 계정의 신청 목록에서 자기 이름은 **지우지 않고 고를 수 없게** 보인다("이미 연결됨 · 구글"). 지우면 본인이 자기 이름을 못 찾아 더 혼란스럽다. 누르면 "이 이름은 이미 다른 로그인 방법으로 신청되어 있습니다. 처음 사용하신 **구글**로 로그인해 주세요" 와 **[구글로 다시 로그인하기]** 버튼(로그아웃 후 `/login`)이 뜬다 — 로그아웃은 수단이고 목적은 맞는 계정으로 다시 들어오는 것이다. 어느 제공자인지 실제로 보여준다. 폐쇄된 청년부 명단이므로 이 정도 노출은 문제가 되지 않는다.

정말 잘못 붙은 연결(남의 계정, 엉뚱한 이름 승인)은 운영자만 뗀다 — `unlink_person_account`(04 §3.3). 화면은 A-1(Step 9)에서. 떼면 계정은 미승인으로 돌아가고 리더 권한도 사라지지만 **주간기록·streak 은 사람에 남는다.** 본인이 맞는 계정으로 다시 신청→승인하면 이어진다.

**P-7 휴면 승인** — 리더가 L-4a에서 신청하면 이 목록에 쌓인다. 승인 전까지 상태는 '활동'으로 유지되어 지표 분모에 남는다. 승인이 밀리면 사각지대 지표가 오염되므로 대시보드에 대기 건수를 노출한다.

**L-8 목장 꾸미기 (Phase 3)** — 꾸민 결과가 **공개 영역에 노출되어야 보상으로 작동한다.** 목장 페이지는 격리 원칙상 그 목장 리더만 보므로, 꾸미기는 리더보드의 목장 카드와 전체 인원표의 목장 표시에 반영되어야 한다. 이것이 이 보상 설계의 성립 조건이다.

**C-2 온보딩** — 이름의 의미를 반드시 넣는다. "왜 99인가"를 읽고 시작해야 이름이 작동한다(PRD §1).
