## 0. 큰 그림

개발은 크게 세 덩어리다.

```
[ 1단계 : 바닥 다지기 ]   데이터 구조 + 권한
        ↓
[ 2단계 : 핵심 기능 ]     보고서 작성 → 목사님 확인 → 알림
        ↓
[ 3단계 : 주변 기능 ]     프로필 · 관리 · 내보내기 · 인원 등록·이동
```

**1단계를 먼저 하는 이유**가 중요하다. 권한 구조를 나중에 얹으면 이미 만든 화면을 전부 다시 봐야 한다. 이 앱은 "누가 무엇을 볼 수 있는가"가 정체성이므로 그것부터 깔고 간다.

예상 기간은 **주말 위주로 작업한다는 가정**이다. 평일에도 시간을 내면 줄어든다.

## 1단계 — 바닥 다지기

### Step 0. 준비 (반나절)

**하는 일**

- Supabase 계정과 프로젝트 생성
- Vercel 계정 생성, GitHub 저장소 연결
- Next.js 프로젝트 뼈대 만들기

> **환경변수(environment variable)** — 비밀번호나 API 키처럼 코드에 직접 쓰면 안 되는 값을 따로 보관하는 방법. `.env` 파일에 넣고, 이 파일은 `.gitignore`에 있어서 GitHub에 올라가지 않는다. Vercel에는 웹 화면에서 따로 등록한다.

**완료 기준** — 빈 페이지가 인터넷 주소로 열린다.

### Step 1. 데이터베이스 만들기 (2~3일)

**하는 일** — 스키마 문서(04)의 테이블을 실제로 만든다. 명단(persons), 목장, 보고서, 주간기록, 프로필 등.

> **스키마(schema)** — 데이터베이스의 설계도. 어떤 표(테이블)가 있고, 각 표에 어떤 칸(컬럼)이 있는지를 정의한 것.
>
> **마이그레이션(migration)** — 스키마를 바꾸는 작업을 파일로 기록해두는 것. "3월 5일에 이 컬럼을 추가했다"가 파일로 남아서, 나중에 다른 환경에서도 같은 순서로 재현할 수 있다. 수동으로 웹 화면에서 테이블을 만들면 이 기록이 안 남으므로 **반드시 마이그레이션 파일로 관리**한다.
>
> **시드 데이터(seed data)** — 개발·테스트용 가짜 데이터. 목장 3개, 리더 6명, 양 20명 정도를 가명으로 넣어둔다. **실명은 절대 쓰지 않는다** — 이 파일이 GitHub에 올라갈 수 있다.

**완료 기준** — 시드 데이터가 들어가고, 목장별로 조회가 된다.

### Step 2. 권한 설계 ★ (3~5일)

**여기가 이 프로젝트에서 가장 중요한 단계다.**

**하는 일**

- 각 테이블에 RLS 정책을 건다
- 권한 테스트를 작성한다

> **RLS(Row-Level Security, 행 수준 보안)** — 데이터베이스가 행 단위로 접근을 판단하는 기능. "3목장 리더에게는 3목장 행만 내준다"는 규칙을 테이블 자체에 걸어두면, 코드에서 조건을 빼먹어도 다른 목장 데이터가 나오지 않는다.
>
> **정책(policy)** — RLS의 규칙 하나하나. 읽기·쓰기·수정·삭제마다 따로 건다.
>
> **테스트(test)** — 코드가 의도대로 동작하는지 자동으로 확인하는 코드. 한 번 만들어두면 나중에 뭘 고쳐도 다시 돌려서 확인할 수 있다.

**반드시 만들어야 할 테스트**

| 테스트 | 기대 결과 |
|---|---|
| 3목장 리더가 3목장 기록 조회 | 성공 |
| 3목장 리더가 7목장 기록 조회 | **반드시 실패** |
| 3목장 리더가 7목장 기록 수정 | **반드시 실패** |
| 목사님이 전체 조회 | 성공 |
| 운영자가 보고서 본문 조회 | **반드시 실패** |

**완료 기준** — 위 테스트가 전부 통과한다. 이게 통과하기 전에는 화면을 만들지 않는다.

## 2단계 — 핵심 기능

### Step 3. 로그인 (3~4일)

**하는 일** — 카카오·구글 로그인, 세션 관리, 신청·승인으로 계정 연결.

> **OAuth** — "카카오로 로그인" 같은 방식의 표준. 우리 앱이 비밀번호를 직접 받지 않고, 카카오에 "이 사람이 본인 맞나요?"를 물어보는 구조다. 비밀번호를 저장할 필요가 없어서 더 안전하다.
>
> **원래는 초대 토큰 방식이었다.** 운영자가 리더 50명에게 1회용 링크를 보내는 구조였는데, Step 3.5 에서 청년도 앱을 쓰게 되면서 운영자가 80명에게 링크를 보내는 것이 병목이 되어 바꿨다.

**주의** — Supabase는 기본적으로 누구나 가입할 수 있다. 막지 않는다. 대신 **승인 전에는 아무것도 못 보게** 한다.

**완료 기준** — 로그인 → 미승인 → 신청 → 리더 승인 → 청년 흐름이 화면에서 이어진다. 미승인 상태로는 청년부 프로필 외에 아무것도 보이지 않는다.

> **바뀜** — 청년 흐름은 없다(2026-09-27, 청년 계정 없음은 2026-10-16 확정). 2026-10-30 부터 처음 로그인하면 **목사님 · 임원진 · 리더** 중 하나를 고르고 운영자가 승인한다(§5단계).

### Step 3.5. 데이터 모델 통합과 권한 재작업 (2~3일)

조직 구조에 대한 이해가 바뀌어 중간에 끼워 넣은 단계다. 전제 셋이 틀렸다 — 규모(150 → 80명), 대상(리더도 기록 대상), 사용자(청년도 앱을 쓴다). 스키마 문서 §0 에 근거가 있다.

> **되돌림 (2026-09-27, 04-schema §0 v0.7)** — 세 번째는 같은 날 다시 뒤집었다. **앱을 청년에게는 공유하지 않는다.** 사용자는 리더·목사님·운영자뿐, 역할 4단계(`member` 삭제), 신청은 리더 전용, 승인은 운영자만. `persons` 의 청년 행과 기록 대상으로서의 청년은 그대로다.

**한 일**

- `members` + `leaders` → `persons` 하나로. 목장 내 역할·목장장 여부는 컬럼으로
- 역할 3단계 → 5단계 → 4단계 (`pending / leader / pastor / admin`)
- 초대 토큰 제거 → 신청·승인 함수. 신청은 리더 명단만, 승인·거절은 운영자만(2026-09-27). 리더 권한은 명단이 기준이라 운영자 겸임이 된다
- 자기 자신에 대한 1대1 접촉은 저장 시 무효(트리거)
- 미승인 계정에게 출석·보고서의 존재를 숨긴다 — 권한 없는 조회는 빈 결과, 권한 없는 화면은 404

> **403 이 아니라 404 인 이유** — 403 은 "거기 뭔가 있는데 너는 못 본다" 를 알려준다. 원래 근거는 청년 은닉이었고, 청년 계정이 없어진 뒤에도 미승인 계정에 같은 방식을 유지한다 — 한 가지 방식으로만 답하는 편이 단순하다.

**완료 기준** — `npm run test:rls` 전부 통과(83건 → 2026-09-27 현재 133건). 문서와 스키마 일치.

### Step 4. 보고서 작성 화면 (5~7일)

**제품의 심장이다.** 리더가 매주 쓰는 유일한 화면이고, 여기가 불편하면 앱 전체가 죽는다.

**하는 일**

- 목장 양 목록 표시
- 출석 3단 토글 (결석 / 예배만 / 예배+목장)
- 1대1 접촉 체크
- 기도제목·특이사항 입력
- 지난주 기도제목 자동 표시
- 제출

**완료 기준** — **본인이 직접 써보고 3분 안에 끝나는가.** 시간을 재본다. 안 되면 화면을 고친다.

> **구현 상태 (2026-09-27)** — 화면과 쓰기 경로(`submit_report`)가 들어갔다. 한 화면에 목장 전원, 출석 3단(기본값 없음), 빈 기도제목 무강조, 가장 최근 기록의 기도제목 표시, 바뀐 필드만 제출, 행 단위 충돌 감지, 접속 표시, 로컬 임시 보관(복원은 opt-in — 배너의 '복원' 을 눌러야 폼에 들어간다, 7일 만료). 마감 후 저장은 지각으로 남는다. 화면 배선은 `npm run test:ui`(vitest + jsdom) 가 잡는다 — 첫 케이스는 "사본이 있는 채로 열어 아무것도 안 누르고 제출하면 서버 값 그대로". **실제 소요 시간은 아직 재지 않았다** — 실제 로그인이 필요해 자동화할 수 없다. **측정 기준값 — 시드 3목장(7명) 전부 새로 쓸 때 16탭 + 입력 7건.** '이어서 쓰기' 로 줄인 수치(16탭 + 입력 1건)는 기준값으로 쓰지 않는다. 그 경로를 상시로 타면 기도제목이 지난주 복사본으로 굳고, 사각지대 판정의 입력 — 이번 주에 실제로 나눈 것 — 이 죽는다.

> **출석 v2 (2026-10-30)** — 3단 토글을 네 칩으로 바꿨다: 현장 예배 · 현장 예배 + 목장 불참 · 온라인 예배 · 결석. 온라인 · 목장 불참 · 결석을 고르면 각각 사유 한 칸. 제출 단추는 맨 밑(2026-10-23). '1대1' 은 화면에서 '컨택'(2026-10-23).

> 이 시점에 리더 2~3명에게 보여주고 피드백을 받으면 좋다. 완성 후가 아니라 지금이 고치기 제일 쉬운 때다.

> **실명단 도입 (2026-09-28)** — 원격에 실제 명단 109명(리더 42·양 67, 목장 12)이 들어갔다. `npm run roster:import`, 09 §1.4. 가명 시드는 로컬 테스트 픽스처로만 남는다. Step 6~8 개발용 데모 기록 4주가 실명단 위에 있다(`demo:clear` 로 제거).
>
> **명단 정제 + 상태 태그 (2026-09-30)** — 110명(리더 **41** · 양 69). 하품 목장 리더 1명이 타 교회 출석으로 리더 해제·기록 제외(09 §1.5). **리더 계정 승인 대상 41명.** `care_status` 태그 17명(군 복무 3 · 원거리 6 · 주말 근무 2 · 타 교회 4 · 장기 미출석 2), 사각지대 첫 기준점 `needs_check` 24명 — 1회성, 재도입이 되돌리지 않는다(04 v0.12).

### Step 5. 목사님 화면 (3~4일)

**하는 일** — 이번 주 제출 현황(P-1 `/pastor`), 목장별 보고서 열람(P-3, 읽기 전용), 읽음 자동 기록, 스탬프 한 탭, 리더 화면에 "확인하셨습니다" 한 줄.

**완료 기준** — 12개 보고서를 훑는 탭 수를 센다: 제출된 목장 N 개에 첫 카드 1탭 + 스탬프(=다음) N탭 = **N+1**. 10개 제출이면 11탭. 목사님의 부담이 크면 반응 루프가 끊기고, 그러면 리더가 이탈한다.

> **구현 상태 (2026-09-28)** — 들어갔다. 한 줄 코멘트는 보류(매주 12개에 글을 쓰는 설계는 다시 0 이 된다) — 반응은 스탬프 하나("기도하겠습니다"), 누르면 다음 목장으로. 연타는 막지 않고 열람 시간 중앙값으로 관찰(03 §2.2c). 지표는 열람률·반응률 둘로 분리(03 §2.2). 사각지대·내보내기는 Step 6·10. `tests/rls/pastor-review.test.mjs` 15건.

**하는 일** — 챙김이 필요한 양, 단독 연결, 관계 밀도, 성별 수급 계산.

> **SECURITY DEFINER 함수** — 데이터베이스 안에서 도는 작은 프로그램인데, **RLS를 통과할 수 있는 특별 권한**을 갖는다. 사각지대 판정은 그 양의 전체 기록을 봐야 하는데(다른 목장 기록 포함) 리더 권한으로는 못 보니, 이 함수가 대신 계산해서 **결과 숫자만** 돌려준다.
>
> 핵심은 **원문은 절대 돌려주지 않는 것**이다. 리더는 "이 양은 접촉 공백"이라는 사실만 알고, 근거가 된 다른 목장 기록은 못 본다.

**완료 기준** — 시드 데이터로 계산한 값이 손으로 센 값과 일치한다.

### Step 7. 알림 (4~5일)

**하는 일** — 웹 푸시 발송, 월요일 자동 실행.

> **서비스 워커(service worker)** — 웹페이지가 닫혀 있어도 백그라운드에서 도는 작은 프로그램. 푸시 알림을 받으려면 반드시 필요하고, PWA가 앱처럼 동작하게 만드는 핵심이기도 하다.
>
> **VAPID** — 웹 푸시를 보낼 때 "이 알림은 우리 서버가 보낸 게 맞다"를 증명하는 열쇠 한 쌍. 한 번 만들어서 환경변수에 넣어두면 된다.
>
> **크론(cron)** — 정해진 시각에 자동으로 실행되는 예약 작업. "매주 월요일 오후 8시에 미제출 목장을 찾아 알림 보내기" 같은 것.

**주의** — iOS는 홈 화면에 추가해야만 알림이 온다. 온보딩에 그 단계를 넣고, 아이폰으로 직접 테스트해봐야 한다.

**완료 기준** — 본인 폰(안드로이드·아이폰 각각)으로 알림이 실제로 온다.

| 크론 | 정해진 시각에 자동 실행되는 예약 작업 |
| 환경변수 | 코드에 넣으면 안 되는 비밀값을 따로 두는 곳 |
